# Vercel container deployment

This directory is the Vercel project root. It deploys the complete LiteLLM gateway using the official v1.104.0 image, pinned to its verified multi-platform registry digest. Vercel Container Images is a beta feature. No credentials belong in this directory.

Run `vercel --prod` from `config/vercel` after linking the intended Vercel project and configuring its private environment variables. Use a Vercel CLI version that supports Container Images and Services; the deployment was prepared with the explicit `services.gateway` entrypoint in `vercel.json` because older automatic Dockerfile detection produced a static deployment. Vercel may require the account owner to accept beta terms in the browser before the container build can run. An agent cannot accept those terms for the owner.

Copy the fork's patched `model_prices_and_context_window.json` into this directory as `pricing.json` before building. The image replaces its packaged pricing catalogue with this snapshot and disables automatic upstream catalogue replacement. Refresh the snapshot and redeploy when prices change. The only exposed model is the verified deployment `gpt-6-astra`; its Global Standard deployment uses `azure/gpt-6-astra` pricing rather than `azure/us/gpt-6-astra`. Other models present in the pricing catalogue are not automatically deployed in Azure.

Set private Production variables `AZURE_API_BASE`, `AZURE_API_KEY`, `DATABASE_URL`, `REDIS_URL`, `LITELLM_MASTER_KEY`, and `LITELLM_SALT_KEY`. The Azure base is the resource HTTPS endpoint without `/openai/v1`; the adapter adds that path. Both LiteLLM secrets must be at least 32 characters; the master key must start with `sk-`. Keep the salt stable because it protects stored credentials. `REDIS_URL` must be a TCP `redis://` or TLS `rediss://` URL, not an HTTP REST endpoint. When Redis is absent, the Admin UI can open but a mandatory inference pre-call hook returns HTTP 503 before forwarding inference. Add Redis and redeploy to enable paid requests. A configured Redis must pass startup checks and an availability check before each inference request.

Use a dedicated LiteLLM PostgreSQL database. Apply the release's migrations once in a separate job before deployment, using the schema and migration directory shipped in `litellm-proxy-extras/litellm_proxy_extras`. A direct Neon connection is appropriate for migration jobs. The `LITELLM_RUN_MIGRATIONS=true` option is available for persistent local containers, but initialization can exceed Vercel's approximately 28-second container startup window; keep it `false` on Vercel. The container runs LiteLLM's native FastAPI application through Uvicorn with `CONFIG_FILE_PATH`, avoiding repeated CLI migration introspection. Runtime schema changes are disabled. Readiness must pass before issuing keys. Do not reuse the custom proxy's database tables or expose this production database to Preview deployments.

For a completely empty database, the native `litellm --use_prisma_db_push --skip_server_startup --enforce_prisma_migration_check` initialization is supported. It can remove data, so use it only on a new database. Afterwards, run the same release's native v2 migration entrypoint to verify schema equality and record its migration baseline before upgrading. This deployment uses the separate `litellm_proxy` database; all 189 release migration names and checksums were verified. Do not switch an interrupted migration database to schema push.

The entrypoint binds the listening socket before importing LiteLLM and passes that socket to Uvicorn. HTTP requests are handled only after LiteLLM's native startup completes; this avoids intermittent container startup failures. Initial requests can still be slower while the container starts. Windows line endings are normalized during the image build.

The generated `pricing.json`, local `.env` files, and `.vercel` account linkage are ignored by Git. Deployment credentials stay in private Vercel variables. A different authorized account can link this directory to its own project and provide its own variables without a Codex session dependency.

Create one virtual key per person with a configurable `max_budget` through the Admin UI or `/key/generate`. Leave `budget_duration` unset for a lifetime cap and do not attach a `team_id` unless shared team accounting is intended. No per-key budget amount is hardcoded here. Give teammates their generated virtual key and this deployment's `/v1` base URL; keep the master key and Azure key private.

Budget reservations and fail-closed enforcement are enabled, with Redis coordination and short batch spend flushing. Response caching is disabled. Azure requests use v1, retries are disabled, and requests time out before Vercel's default 300-second function limit. The native model output limit remains unchanged; callers should explicitly bound `max_completion_tokens` or `max_output_tokens` so reservations reflect the requested maximum output.

Vercel container instances scale to zero after five idle minutes in Production and thirty seconds in Preview, and receive a thirty-second shutdown grace period. Scheduled jobs pause at zero instances. This configuration is a deployment trial, not a proven invoice-exact spending guarantee. Verify concurrent budget exhaustion, revocation, streaming interruption, failed Azure calls, and spend survival after idle scale-down and restarts before assigning substantial budgets. Background Responses and asynchronous batches require additional durable worker handling.

The deployment uses only Azure inference credentials. Azure Reader application credentials are separate and do not authenticate model requests. Cost estimates use recorded usage and the pinned pricing snapshot, not a live Azure invoice.

Official references: [Vercel Container Images](https://vercel.com/docs/functions/container-images), [LiteLLM budget enforcement](https://docs.litellm.ai/docs/proxy/users), and [LiteLLM deployment guidance](https://docs.litellm.ai/docs/proxy/prod).
